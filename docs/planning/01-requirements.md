# Требования PDF и состояние проекта

Дата анализа: 16 сентября 2026 года. Источник прочитан полностью: 22 страницы
файла [`Эффективный бизнес.pdf`](../../Эффективный%20бизнес.pdf). Номера ниже
соответствуют напечатанным номерам страниц PDF.

## Задача трека

Трек требует создать чат-бота или мини-приложение на Платформе для бизнеса в
MAX, которое решает актуальную задачу предпринимателей или компаний и имеет
практическую ценность для выбранной аудитории (PDF, с. 2, 6).

Кадры для бизнеса и сельского хозяйства прямо названы одним из допустимых
направлений: поиск работников, сезонная занятость, стажировки, обучение,
кадровые потребности и взаимодействие с образовательными организациями (PDF,
с. 5). Это отраслевой контекст, а не требование реализовать все перечисленные
функции: команда должна самостоятельно выбрать проблему, пользователя и модель
B2C/B2B/B2G (PDF, с. 5, 16).

Онлайн-этап требует определить сегмент, подтвердить проблему, спроектировать UX,
создать работающий в MAX MVP, определить эффект и масштабирование и подготовить
презентацию. Для финала дополнительно нужны сценарий пилота, доработка,
демонстрация и командная защита (PDF, с. 6).

| № | Требование PDF | Следствие для проекта |

PDF рекомендует узкий сегмент, подтверждение проблемы, один приоритетный
сквозной сценарий, выбор технологии после задачи, честную маркировку модельных
данных и конкретную схему масштабирования (с. 8).

## Формат сдачи

### Обязательно для всех решений

| Артефакт | Точное требование | Страница |
|---|---|---:|
| Работающее решение | Ссылка/способ доступа к боту или мини-приложению для полного основного сценария | 9 |
| Зафиксированный код | Git-репозиторий с commit hash либо архив с checksum; версия замораживается после дедлайна | 9 |
| README | Назначение, сценарий, архитектура, одна команда запуска Docker, environment/переменные/порты/зависимости, интеграции/данные, тестовые данные, пошаговая проверка, ожидаемое поведение, ограничения, stop/restart | 9 |
| Зависимости | Файл с зафиксированными библиотеками и версиями | 9 |
| Docker | Dockerfile для локальных компонентов, Compose с запуском одной командой, `.dockerignore`, `.env.example` без секретов | 9 |
| Время сборки | Не более 5 минут без первоначальной загрузки базовых образов; без избыточных операций | 9 |
| Презентация | PDF; первый неоцениваемый слайд содержит технический доступ, repo/commit, API, тестовые учётные записи, необходимые проверочные secrets и краткий сценарий | 10 |
| Продуктовая часть | Со второго слайда: команда, summary, сегмент/проблема, решение/путь, эффект, архитектура, данные/интеграции, масштабирование, риски/допущения, источники | 10 |

Проверочные secrets нельзя коммитить: ограниченные, отзывные значения передаются
только в техническом слайде/разрешённом канале сдачи. Это одновременно выполняет
страницу 10 и запрет страницы 7.

### Дополнительно, потому что у решения есть собственный Django API

- полный HTTPS-адрес проверяемого API;
- `openapi.yaml` или `openapi.json` версии OpenAPI 3.0/3.1;
- тестовые учётные записи для обязательных ролей;
- воспроизводимые тестовые данные;
- `DATA-API.yaml`: версия схемы, решение/команда, base URL, обязательные проверки,
  HTTP method/path, параметры/headers/body, роль, ожидаемые status codes, content
  type/JSON structure/required fields (PDF, с. 10).

Эти артефакты добавлены в отдельную задачу `DELIV-001`.

## Допуск и критерии

### Основания для недопуска

Решение получает 0 и дальше не оценивается, если выполняется хотя бы одно
условие (PDF, с. 11):

1. проект не по теме, не связан с кейсом или не использует MAX как среду;
2. бот/мини-приложение не запускается, не отвечает либо основной сценарий нельзя
   проверить;
3. отсутствует презентация.

### Онлайн-этап

Каждый критерий оценивается от 0 до 3: 0 — невозможно оценить/не выполнено,
1 — существенные пробелы, 2 — в основном выполнено с недочётами, 3 — полно и
качественно (PDF, с. 11).

Продуктовая оценка — 40% итогового онлайн-балла (PDF, с. 12):

| Критерий | Вес внутри продукта | Эффективный вес онлайн |
|---|---:|---:|
| Потенциал масштабирования | 35% | 14% |
| Пользовательская ценность | 25% | 10% |
| UX/UI и удобство | 20% | 8% |
| Обоснованность и целостность | 15% | 6% |
| Качество презентации | 5% | 2% |

Техническая оценка — 60% итогового онлайн-балла (PDF, с. 13):

| Критерий | Вес внутри техники | Эффективный вес онлайн |
|---|---:|---:|
| Работоспособность и полнота основных функций | 30% | 18% |
| Корректность интеграции и обмена данными | 20% | 12% |
| Техническая реализация и архитектура | 20% | 12% |
| Стабильность и обработка ошибок | 10% | 6% |
| Безопасность, зависимости и данные | 10% | 6% |
| Техническая документация и комплектность | 10% | 6% |

Платформенный бонус `+0,15` начисляется только целиком на онлайн-этапе: базовый
сценарий должен работать, а дополнительная возможность MAX — создавать ценность,
быть органично встроена, работать сквозным образом и быть описана. Свой API или
лишние функции бонуса не дают (PDF, с. 13). Market update в канале с возвратом
по диплинку в dashboard может стать кандидатом на
бонус, но план не считает его гарантированным.

### Финал

Результат финала: 40% технической оценки продукта и 60% защиты; онлайн-бонус не
переносится (PDF, с. 14). В оценке защиты:

| Критерий | Вес |
|---|---:|
| Пользовательская ценность и соответствие задаче | 25% |
| Масштабирование и тиражирование | 25% |
| Качество MVP и пользовательского опыта | 20% |
| Сценарий запуска и внедрения | 15% |
| Качество защиты и ответов | 10% |
| Командное владение решением | 5% |

Следовательно, план пилота и конкретное масштабирование — обязательные
презентационные результаты, а не общие фразы «на всю Россию» (PDF, с. 19–20).

## MAX, данные и источники

- MAX предоставляет Bot API, MAX Bridge и MAX UI; мини-приложение подключается к
  боту и работает по HTTPS. Токен бота выдаётся организаторами (PDF, с. 15).
- Актуальную документацию и changelog нужно повторно проверить перед разработкой
  и сдачей (PDF, с. 15).
- Официальные данные должны иметь источник, территорию/период и дату
  актуальности; факты отделяются от расчётов, рекомендаций и допущений (с. 18).
- Недоступная интеграция не имитируется: используются явно маркированные
  синтетические/подготовленные данные с описанием post-MVP подключения (с. 18).
- «Работа России» прямо приведена как официальный ресурс для исследования
  кадровых потребностей и сценариев найма (PDF, с. 21).

## Состояние репозитория

Состояние определено чтением файлов. Live-запуск Compose в рамках планирования
не выполнялся.

### Уже реализовано и переиспользуется

- `compose.yaml`: PostgreSQL 17.6, backend/frontend, DB healthcheck, volumes,
  стандартные порты `8000`/`5173`.
- `backend/`: Django 5.2.6, DRF 3.16.1, psycopg, drf-spectacular, pytest, Ruff.
- `apps.users.User` создан до продуктовых миграций.
- `GET /api/health/` проверяет БД и скрывает детали исключения; есть два теста.
- Django Admin, OpenAPI schema и Swagger UI уже подключены.
- React 19, strict TypeScript, Router, TanStack Query и Vite proxy уже настроены.
- `.env.example`, lock-файлы, Dockerfiles, `.dockerignore` и dev README есть.

Эти работы не дублируются в backlog. Но существующая OpenAPI schema ещё не
доказывает выполнение страницы 10: нужны продуктовые endpoints, экспорт schema,
`DATA-API.yaml`, test accounts/data и live HTTPS verification.

### Подтверждённые пробелы

| Пробел | Основание в коде | Связь с PDF |
|---|---|---|
| Нет предметной модели/API | Кроме `User` продуктовых моделей нет | Нужны company, vacancy monitor, market snapshot и alert |
| Нет MAX-auth/Bridge/bot/webhook | Нет интеграционного кода | Обязательны вход, channel binding и реальный post |
| Нет ролей и объектных прав | DRF permissions не настроены | Компания и её мониторинг должны быть изолированы |
| Нет продуктового UI | Только healthcheck screen | Нужны vacancy form, dashboard и channel setup |
| Нет внешнего адаптера/расчёта | Нет trudvsem adapter и benchmark service | Live источник является Must, а не дополнением |
| Только local delivery | Нет public HTTPS/production settings | Проверка MAX/API, с. 9–10, 15 |
| Нет submission API bundle | Нет `DATA-API.yaml`, test accounts/data | Собственный API, с. 10 |
| Нет материалов презентации/пилота | Нет slides/evidence/pilot plan | Сдача и финал, с. 10, 14, 20 |

Healthcheck, Swagger, custom user и Compose считаются готовой основой, а не
новыми backlog-задачами. Их проверка входит в общий delivery gate.
